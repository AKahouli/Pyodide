# Global agent rules

- External library, framework, SDK, or CLI questions: use the Context7 MCP (`resolve-library-id`, then `query-docs` scoped to one concept) before answering from memory. Load the `context7-mcp` skill for the full recipe. Not for business logic, refactoring, or code review.
- Keep replies short and factual. Give a concise update at a real milestone, blocker, or background launch; avoid tool-by-tool narration and restating the request.
- Read files by section or line range. Reuse current session evidence instead of re-reading unchanged material.
- Prefer independent tool calls and bounded subagent tasks in parallel. Native Task `background: true` returns immediately and notifies on completion when enabled; continue unrelated work and do not poll or duplicate the task.

## Questions and autonomy

- Creating a new database schema/namespace, table, collection, frontend/backend module, service, runtime or microservice is a user decision: inspect existing reuse options, prepare the concrete design and obtain confirmation before implementation. An explicit current approval of that named design counts; broad feature/end-to-end approval does not. Preserve the approved scope and message reference in task checkpoint decisions/handoffs. Pause dependent edits while awaiting the answer, continue independent work, and do not repeat confirmation for an unchanged approved design. In opted-in repositories follow `docs/agent-context/architecture/change-control.md`.
- Assess documentation impact on every task. Update affected owning architecture references and ADRs for changed durable decisions/boundaries; supersede accepted ADRs rather than rewriting their history. Background documentation work may follow ready-to-test delivery, but full completion requires reviewed relevant updates or a recorded no-impact reason.

- The primary agent owns questions to the user; specialists return the exact missing information to it. First inspect available context. Ask only when an unresolved choice materially changes the outcome, scope, access, or acceptance criteria. Bundle related questions; use a stated, reversible default for minor details. Continue independent work while a necessary answer is pending.
- Within the agreed request, perform implementation, checks, fixes, and delegation without asking for confirmation at each step. Honor actual permission gates and user-requested stopping points. New user feedback steers the active task; it does not reset discovery or settled decisions.
- Shell commands use native OpenCode permissions, independently of graph/memory/checkpoint health. Run authorized existing runtime scripts and collect scoped logs when needed; inspect scripts first and respect shared ports/processes/data in parallel sessions. Restricted specialists return command needs to the primary. Use guarded native edit tools for authored source/document changes; do not bypass preparation or file ownership through shell writes.
- For work with multiple substantial, independently testable phases, ask once at kickoff: finish end to end or pause after each completed, testable phase. Reuse a choice already confirmed for the current task; do not turn one task's answer into a permanent preference. End to end means continue through all agreed phases with concise milestone updates. Phase pauses mean deliver the completed phase's evidence and testing instructions, then wait for the user's decision before starting the next phase.

## CRG: graph-first code work

- Use automatic per-session health reports; do not repeat graph-statistics, `hindsight_diagnose` or `sdlc_health` calls at startup. Report failures once or when status changes. Graph/Hindsight failures and pending checks never block coding: use focused source/search/tests for graph context and Git docs/checkpoints for memory. Recovery can run alongside authorized work; refresh health after recovery. Actual checkpoint storage/ownership failures still block native edits. Report a missing/stale plugin and fully restart the host after installation; a new chat does not reload it.

- When the SDLC plugin is active, checkpoint intent/progress, read scoped docs/code, and prepare exact targets with a reuse decision before edits. Preserve task IDs through handoffs; use `sdlc_diff(file, taskID)` for scoped review. New unrelated work in the same chat uses `sdlc_checkpoint(newTask: true)`; same-task corrections reopen with `status: active`. Resume from persisted state rather than restarting discovery.

- Start a new code investigation with `get_minimal_context_tool(task=..., repo_root=...)`. Reuse a caller's current scoped graph evidence instead of repeating this in every specialist. Pass the active repository/worktree's absolute `repo_root` to every repository-scoped graph call.
- Load `crg-navigation` for task-specific recipes. Prefer targeted queries, `detail_level="minimal"`, bounded results, and depth 1-2. Aim for about five graph calls / 800 output tokens per investigation, expanding only when correctness requires it.
- If the graph is missing/stale, use focused source search immediately. Refresh incrementally when needed for a remaining impact question and check the result; read-only subagents report refresh needs. Recheck after branch switches or external edits; matching HEAD does not establish working-tree freshness.
- The graph narrows scope; source and executable tests remain authoritative. Empty results, unresolved calls, partial builds, dynamic dispatch, and serialized boundaries require targeted source verification. If CRG is unavailable or cannot answer, use focused Grep/Glob/Read and record the limitation in the handoff.
- For review, reuse verified graph freshness or review the scoped diff/source/tests directly. Refresh only for an unresolved impact question. Supply the actual review base and changed files; do not default to `HEAD~1` for uncommitted work or a whole-branch review.
- Skip CRG for pure prose, trivial text edits, and git-only chores. Do not run architecture listings, embeddings, or full rebuilds routinely. Keep graph data isolated per repository/worktree.
- The shared `crg-daemon` manages watching via `~/.code-review-graph/watch.toml`; MCP servers serve queries without `--auto-watch`. Do not add duplicate edit-update hooks. Only configured paths are watched, and daemon liveness does not prove graph freshness; retain explicit-root and freshness checks.

## Clear follow-up after every user message

- End every human-facing answer with **Follow-up:** one or two concrete sentences stating who does what next, where, and the expected result or verification. For ready-to-test work, give the exact route/action and one observable result. For ongoing authorized work, state the agent's next action and continue without routine confirmation. Ask for a decision only when it is actually needed; name that decision. Distinguish a proposal from implemented work. If finished with no next action, say so. Do not substitute an abstract lesson, repeat a settled scope, invent a task, or print `No durable lesson`.
- Only the primary adds this footer; internal specialists return actionable handoffs. Automatic Hindsight capture handles experience persistence separately; do not launch a reflection task or claim memory saved without confirmation.
- Example after UI validation: **Follow-up:** Open `/conversation`, send a message, and stop the response. The stream should stop and the saved conversation should still reopen.
