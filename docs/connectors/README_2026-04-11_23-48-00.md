# Connectors

> **Slug:** `connectors` | **Status:** draft | **Last Updated:** 2026-04-13 18:00 UTC

## Purpose

MCP-based connector integration for playbook steps. Administrators define a catalog of MCP connectors (SharePoint, Google Drive, Notion, Salesforce, etc.) in the admin panel. Users drag connectors from a sidebar onto playbook canvas nodes, configure credentials and actions per step, and the AI agent uses those MCP tools during execution. Connector imports also support transferring files from SharePoint/M365 into workspace documents.

## Scope

### Included
- Connector catalog CRUD (admin panel)
- User-scoped connector credentials management
- Connector discovery via MCP Inspector
- Playbook step-level tool bindings (not agent-level)
- Multiple bindings per step
- Dynamic MCP tool injection at runtime via `playbook_tool_factory.py`
- Frontend drag-and-drop UX with binding configuration modal
- Connector badges on playbook nodes
- Connector transfer import: `mode: file | files | folder` for importing from SharePoint/M365

### Excluded
- Port typing exposed to users (internal only)
- Global agent-level connector bindings
- Real-time MCP connection health monitoring (deferred)
- Connector marketplace (deferred)
- Non-flattened folder structure preservation in workspace (Phase 1)

### Data Flow

1. Admin creates connector in catalog (name, MCP server ref, actions)
2. User configures credentials for a connector
3. User drags connector from sidebar onto a playbook step node
4. Binding modal opens for credential selection, action checkboxes, fixed params
5. Binding stored in `PlaybookTask.toolBindings[]` (persisted to MongoDB)
6. On playbook execution, `tool_bindings` sent via gRPC to ADK
7. `_proto_task_to_dict` decodes bindings, passes to `create_langchain_tools()`
8. `_create_connector_mcp_tools()` creates LangChain tools per binding action
9. Tools merged with agent's native tools for step execution

### Transfer Import Data Flow

1. User initiates import via `ConnectorTransferService.importToWorkspace()`
2. Adapter resolves credentials via `ConnectorAuthService.resolveRuntimeAuth()`
3. For `mode: folder`, adapter recursively enumerates files via Microsoft Graph API
4. Candidates downloaded and uploaded as workspace documents via `WorkspaceDocumentService`
5. Filename collisions resolved using path-derived suffix (`{base}__{path-segments}{ext}`)
6. Imported files become normal workspace documents consumable by workspace context/code interpreter flow

## Requirements

- As an admin, I want to manage a catalog of MCP connectors so that users can integrate external services.
- As an admin, I want to auto-discover tools from an MCP server using the MCP Inspector.
- As a user, I want to drag a connector onto a playbook step so that the AI can use external tools during that step.
- As a user, I want to manage my own connector credentials so that I only see my authorized items.
- As a user, I want to configure which actions are available per step so that I control the AI's tool access.
- As a system, I want to inject MCP tools at runtime so that the agent can call connector tools dynamically.

## API / Interfaces

### Backend Endpoints

**Admin:**
- `GET /admin/connectors` - List all connectors
- `POST /admin/connectors` - Create connector
- `PATCH /admin/connectors/:id` - Update connector
- `DELETE /admin/connectors/:id` - Delete connector
- `POST /admin/connectors/inspect` - MCP Inspector
- `POST /admin/connectors/import-mcp` - Import from MCP server

**User:**
- `GET /connectors` - List active connectors
- `GET /connectors/:id/credentials` - List user credentials
- `POST /connectors/:id/credentials` - Create credential
- `PATCH /connectors/credentials/:id` - Update credential
- `DELETE /connectors/credentials/:id` - Delete credential
- `POST /connectors/credentials/:id/validate` - Validate credential

### Transfer Import API

**`POST /connectors/transfer/import`** — Import files from connector to workspace

Request body (`ImportConnectorItemDto`):
| Field | Type | Description |
|-------|------|-------------|
| `connectorId` | `string` | Connector slug or ID (e.g. `m365`, `gdrive`) |
| `workspaceId` | `string` | Target workspace ID |
| `itemRef` | `Record<string, unknown>` | Item reference from connector (required for `mode: file`) |
| `itemRefs` | `Record<string, unknown>[]` | Multiple item references (required for `mode: files`) |
| `mode` | `'file' \| 'files' \| 'folder'` | Import mode; default: `'file'` |
| `recursive` | `boolean` | Recursively enumerate folder contents; default: `true` |
| `flatten` | `boolean` | Flatten imported folder into workspace files; default: `true` (Phase 1 only) |
| `filename` | `string` | Override filename (single file mode only) |
| `mimeType` | `string` | Override MIME type |

Response (`ImportTransferResult`):
```typescript
{
  success: boolean;
  mode: 'file' | 'files' | 'folder';
  workspaceId: string;
  imported: Array<{
    success: boolean;
    workspaceDocumentId?: string;
    filename?: string;
    finalFilename?: string;
    sourcePath?: string;
    collisionResolved?: boolean;
    error?: string;
  }>;
  summary: { requested: number; imported: number; failed: number };
  errors: Array<{ sourcePath?: string; error: string }>;
}
```

**Transfer Adapter Interface** (`ConnectorTransferAdapter`):
```typescript
interface ConnectorTransferAdapter {
  readonly provider: string;
  resolveImportCandidates?(
    itemRef: Record<string, unknown>,
    authHeaders: Record<string, string>,
    options?: { recursive?: boolean },
  ): Promise<Array<{
    itemRef: Record<string, unknown>;
    filename: string;
    mimeType: string;
    sourcePath: string;
  }>>;
  downloadItem(itemRef, authHeaders): Promise<{ buffer: Buffer; filename: string; mimeType: string }>;
  uploadItem(targetRef, authHeaders, content, filename, mimeType, mode): Promise<{ itemId: string; name: string; webUrl?: string }>;
}
```

### Filename Collision Resolution

When a filename already exists in the workspace, the service generates a collision-safe name:
```
{base}__{path-segment-1_path-segment-2_path-segment-3}{ext}
```
Example: `report.pdf` from `finance/Q1/report.pdf` → `report__q1_report.pdf`

If still colliding, appends a counter: `report__q1_report_2.pdf`

## Design Decisions

| Decision | Rationale | Alternatives Considered |
|----------|-----------|------------------------|
| Step-level bindings, not agent-level | Different steps need different connectors even with the same agent | Agent-level bindings would reduce flexibility |
| Separate `tool_bindings` field on proto | The `Tool` proto is too narrow (name, prompt, description, top_k) | Embedding in tool objects would require breaking proto changes |
| Connector as metadata on existing AI nodes | Connectors are not separate executable nodes | New node types would require significant workflow engine changes |
| `_create_connector_mcp_tools()` in tool factory | Centralized injection point for both full-playbook and single-step paths | Per-step injection would require changes in graph_builder and step_executor separately |
| Flattened folder imports (Phase 1) | Workspace documents are flat; preserving folder structure adds complexity | Nested workspace structures deferred; adapter's `flatten` param future-compatible |
| Path-derived collision suffix | Provides human-readable trace back to source location | Hash-based suffixes are shorter but less interpretable |
| Lazy collision detection | Only resolve collisions when name is already used | Pre-computing all collisions adds overhead for marginal gain |
