# Connectors

> **Slug:** `connectors` | **Status:** stable | **Last Updated:** 2026-04-14 23:35 UTC

## Purpose

MCP-based connector integration for playbook steps and conversation agents. Administrators define a catalog of MCP connectors (SharePoint, Google Drive, Notion, Salesforce, etc.) in the admin panel. Users drag connectors from a sidebar onto playbook canvas nodes, configure credentials and actions per step, and the AI agent uses those MCP tools during execution. Agents can discover files via connector MCP tools and import them into workspace documents for downstream processing (code interpreter, search, etc.).

## Scope

### Included
- Connector catalog CRUD (admin panel)
- User-scoped connector credentials management
- Connector discovery via MCP Inspector
- Playbook step-level tool bindings
- Conversation agent connector bindings
- Multiple bindings per step
- Dynamic MCP tool injection at runtime via `playbook_tool_factory.py` and `connector_tools.py`
- Frontend drag-and-drop UX with binding configuration modal
- Connector badges on playbook nodes
- Connector transfer import: `mode: file | files | folder` for importing from SharePoint/M365
- Agent-facing `<connector>_import_to_workspace` tool auto-generated from connector bindings
- Workspace document persistence with collision-safe filename resolution
- Connector editor skill selection: searchable multi-select component (string array form); replaces prior comma-separated text field

### Excluded
- Port typing exposed to users (internal only)
- Global agent-level connector bindings
- Real-time MCP connection health monitoring (deferred)
- Connector marketplace (deferred)
- Non-flattened folder structure preservation in workspace (Phase 2)
- Async folder import jobs (Phase 2)

### Data Flow

1. Admin creates connector in catalog (name, MCP server ref, actions)
2. User configures credentials for a connector
3. User drags connector from sidebar onto a playbook step node
4. Binding modal opens for credential selection, action checkboxes, fixed params
5. Binding stored in `PlaybookTask.toolBindings[]` (persisted to MongoDB)
6. On playbook execution, `tool_bindings` sent via gRPC to ADK
7. `_proto_task_to_dict` decodes bindings, passes to `create_langchain_tools()`
8. `_create_connector_mcp_tools()` creates LangChain tools per binding action
9. Tools merged with agent's native tools for step execution

### Agent-Driven Import Data Flow

1. Agent calls M365 MCP search/browse tools to discover SharePoint files
2. Agent calls `get_document_content` to inspect or get download URL
3. Agent calls `<connector>_import_to_workspace` tool with the item reference
4. ADK import tool calls `POST /api/v1/connectors/transfer/import` with platform JWT auth
5. Backend `ConnectorTransferService.importToWorkspace()` resolves adapter and auth
6. For `mode: folder`, `M365TransferAdapter.resolveImportCandidates()` recursively enumerates files via Microsoft Graph API
7. Candidates downloaded and uploaded as workspace documents via `WorkspaceDocumentService`
8. Filename collisions resolved using path-derived suffix (`{base}__{path-segments}{ext}`)
9. Imported files become normal workspace documents consumable by workspace context and code interpreter

### Workspace Document Lifecycle

Imported SharePoint files follow the same lifecycle as user-uploaded files:

1. Stored in Azure blob at `{userId}/{workspaceId}/{documentId}/{sanitizedFilename}`
2. Registered as workspace document in MongoDB
3. Exposed via `workspace_context` over gRPC to Python runtime
4. Code interpreter receives `{azure_path, filename}` and mounts files in sandbox
5. Phase 1: flattened (no folder hierarchy preserved)

## Requirements

- As an admin, I want to manage a catalog of MCP connectors so that users can integrate external services.
- As an admin, I want to auto-discover tools from an MCP server using the MCP Inspector.
- As a user, I want to drag a connector onto a playbook step so that the AI can use external tools during that step.
- As a user, I want to manage my own connector credentials so that I only see my authorized items.
- As a user, I want to configure which actions are available per step so that I control the AI's tool access.
- As a system, I want to inject MCP tools at runtime so that the agent can call connector tools dynamically.
- As an agent, I want to search SharePoint and import files into workspace for processing by code interpreter.

- `POST /admin/connectors/inspect` - MCP Inspector
- `POST /admin/connectors/import-mcp` - Import from MCP server

**User:**
- `GET /connectors` - List active connectors
- `GET /connectors/:id/credentials` - List user credentials
- `POST /connectors/:id/credentials` - Create credential
- `PATCH /connectors/credentials/:id` - Update credential
- `DELETE /connectors/credentials/:id` - Delete credential
- `POST /connectors/credentials/:id/validate` - Validate credential

### Transfer Import API

**`POST /api/v1/connectors/transfer/import`** — Import files from connector to workspace

Requires `JwtAuthGuard` with platform JWT.

Request body (`ImportConnectorItemDto`):
| Field | Type | Description |
|-------|------|-------------|
| `connectorId` | `string` | Connector ID (e.g. `69dc21b10be5023e96e4bf84`) |
| `workspaceId` | `string` | Target workspace ID |
| `itemRef` | `Record<string, unknown>` | Item reference (required for `mode: file` or `folder`) |
| `itemRefs` | `Record<string, unknown>[]` | Multiple item references (required for `mode: files`) |
| `mode` | `'file' \| 'files' \| 'folder'` | Import mode; default: `'file'` |
| `recursive` | `boolean` | Recursively enumerate folder contents; default: `true` |
| `flatten` | `boolean` | Flatten imported folder; default: `true` (Phase 1) |
| `filename` | `string` | Override filename (single file mode only) |
| `mimeType` | `string` | Override MIME type |

Item reference shape:
```json
{
  "driveId": "b!1C0tyneZGkCcNl...",
  "itemId": "01HUWYISPHRAY...",
  "path": "optional/path/alternative"
}
```

Response (`ImportTransferResult`):
```typescript
{
  success: boolean;
  mode: 'file' | 'files' | 'folder';
  workspaceId: string;
  imported: Array<{
    success: boolean;
    workspaceDocumentId?: string;
    filename?: string;
    finalFilename?: string;
    mimeType?: string;
    size?: number;
    sourcePath?: string;
    collisionResolved?: boolean;
    error?: string;
  }>;
  summary: { requested: number; imported: number; failed: number };
  errors: Array<{ sourcePath?: string; error: string }>;
}
```

### ADK Import Tool

When a connector binding has auth headers and a workspace is available, the ADK auto-generates an import tool:

**Tool name:** `<connector-slug>_import_to_workspace`

**Accepted input forms:**
1. Direct args: `{ mode, drive_id, item_id }`
2. Direct item ref: `{ mode, item_ref: { driveId, itemId } }`
3. Full MCP result: `{ mode, item_ref: { item: { driveId, itemId, ... } } }`
4. Path-based: `{ mode, drive_id, path: "Folder/File.xlsx" }`

**Auth:** Platform JWT signed with `NESTJS_JWT_SECRET` (not connector OAuth bearer).

### Transfer Adapter Interface

```typescript
interface ConnectorTransferAdapter {
  readonly provider: string;
  resolveImportCandidates?(
    itemRef: Record<string, unknown>,
    authHeaders: Record<string, string>,
    options?: { recursive?: boolean },
  ): Promise<Array<{
    itemRef: Record<string, unknown>;
    filename: string;
    mimeType: string;
    sourcePath: string;

  downloadItem(itemRef, authHeaders): Promise<{ buffer: Buffer; filename: string; mimeType: string }>;
  uploadItem(targetRef, authHeaders, content, filename, mimeType, mode): Promise<{ itemId: string; name: string; webUrl?: string }>;
}
```

### Filename Collision Resolution

When a filename already exists in the workspace, the service generates a collision-safe name:
```
{base}__{path-segment-1_path-segment-2_path-segment-3}{ext}
```
Example: `report.pdf` from `finance/Q1/report.pdf` -> `report__q1_report.pdf`

If still colliding, appends a counter: `report__q1_report_2.pdf`

## Design Decisions

| Decision | Rationale | Alternatives Considered |
|----------|-----------|------------------------|
| Step-level bindings, not agent-level | Different steps need different connectors even with the same agent | Agent-level bindings would reduce flexibility |
| Separate `tool_bindings` field on proto | The `Tool` proto is too narrow (name, prompt, description, top_k) | Embedding in tool objects would require breaking proto changes |
| Connector as metadata on existing AI nodes | Connectors are not separate executable nodes | New node types would require significant workflow engine changes |
| Auto-generated import tool from bindings | Agent needs a single action to persist discovered files into workspace | Manual HTTP calls or raw MCP bridge too complex for LLM orchestration |
| Platform JWT for import auth, not connector OAuth | NestJS JwtAuthGuard validates platform tokens, not connector OAuth bearers | Passing connector token through would require NestJS to accept foreign tokens |
| `NESTJS_JWT_SECRET` separate from `SECRET_KEY` | ADK and NestJS may have different JWT secrets for different auth domains | Unifying secrets couples internal ADK auth to backend auth |
| Workspace from `brain_documents` over `conversation_brain_id` | Brain IDs can be transient; document workspace IDs are persisted | Transient IDs cause "Workspace not found" errors |
| Richer item references in MCP | Prevents LLM from mixing driveId/itemId across search results | Minimal fields (just driveId/itemId) cause 404 when mixed |
| Flattened folder imports (Phase 1) | Workspace documents are flat; preserving folder structure adds complexity | Nested workspace structures deferred; adapter `flatten` param future-compatible |
| Path-derived collision suffix | Provides human-readable trace back to source location | Hash-based suffixes are shorter but less interpretable |
| Lazy collision detection | Only resolve collisions when name is already used | Pre-computing all collisions adds overhead for marginal gain |
