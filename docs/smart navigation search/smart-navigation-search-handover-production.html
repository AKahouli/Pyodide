Smart Navigation Search

How the Logical Search MCP discovers the right document area, returns bounded evidence, navigates structural context, and produces citation-ready answers without flooding the agent context.

Branch: feature/fixes-for-production Snapshot: 2a446f9153f2a6f997bdcfbd125c9a81fcf881b8 MCP: FastMCP + FastAPI Storage: PostgreSQL + pgvector + pg_search

1. The mental model

Smart Navigation is not “vector search”.
It is a staged evidence-retrieval system: constrain the authorized corpus in SQL, discover the most relevant logical areas, return bounded exact evidence, navigate only when needed, and validate citations at the end.
Scope

Constrain before ranking

The production path keeps large workspace scope in PostgreSQL through SearchScope; Python receives bounded candidate metadata rather than the whole corpus.

Discover

Find where to look

One hybrid search call ranks sections and blocks using semantic, lexical and bounded filename signals.

Focus

Find the exact evidence

search_in_sections searches inside already selected sections without re-searching the whole workspace.

Navigate

Read structure only when needed

Ancestors, descendants and context expansion remain optional; the default search skips hierarchy loading.

Bound

Protect context and capacity

Evidence, DB workers and model work all have bounded budgets/queues with explicit degraded-mode behavior.

Verify

Cite exact source locations

Block/image IDs are validated against stored evidence and mapped to page-level citation locations in the terminal citation call.

Question→ SQL scope→ One search pass→ Exact evidence→ Optional focused follow-up→ Citation lookup→ Answer

2. What changed in feature/fixes-for-production

The production branch is eight commits ahead of the snapshot used for the previous handover. The changes alter both the public MCP contract and the internal retrieval path.

Public contract

Document identity is now document_id

get_document_strategy, read_content and search use indexed LogicalDocument.id. Public MCP responses strip file_name and identify document groups with document_id.

Agent control

No server-side rewrite loop

activate_loop and loop_counter are gone. The agent inspects evidence, rewrites only for a concrete unresolved gap, and may pass exclude_section_ids to discover different sections.

Scale

Scope stays in PostgreSQL

SearchScope avoids loading whole-workspace document metadata or giant document-ID lists into Python. Candidate metadata is hydrated only after bounded retrieval.

Ranking

Filename relevance is an internal signal

The default final blend is 75% block RRF, 20% section RRF and 5% filename relevance. When filename semantics are enabled, that 5% is split 3% text / 2% semantic.

Capacity

Bounded waiting queues

DB and model admission now have queue limits in addition to running-worker limits. Overload becomes a retryable condition instead of unbounded waiting.

Operations

Production setup + load testing

The branch adds database-index verification/apply scripts and a real MCP load-test runner for p50/p95/p99, throughput, response size and errors.

Migration note for developers: if code, prompts, tests or clients still refer to file_name as the MCP document scope, or to activate_loop/loop_counter, they are using the previous contract.

3. Architecture overview

Smart Navigation core optional model stages persistent logical index
Production ownership boundary: the Vectorstore owns schema population and indexing. The MCP is a read-only schema consumer. The scalable search path changes how scope and candidates are queried; it does not move source documents or embeddings out of PostgreSQL.

6. What happens inside search

1 — Validate request + authorization scopeQuery and workspace are required. Optional document_id can narrow the authorized scope; exclude_section_ids is validated as positive public integer IDs.
2 — Build one request-local SearchContextWith scalable scope enabled, SearchScope stores SQL predicates/config groups instead of materializing whole-workspace metadata in Python.
3 — Prepare three independent signals concurrentlyFresh query embedding, multilingual lexical variants, and optional bounded filename-semantic scores run under one request deadline.
4 — Run section and block candidate channelsVector and BM25/FTS candidate queries run inside the scoped corpus. Excluded public section IDs are filtered before candidate limits.
5 — Add filename context and fuseBlock, section and filename ranks are combined with configured weights. Exact structured issuer matches can narrow the document set.
6 — Hydrate bounded winners onlyCandidate document metadata, section metadata, block counts/pages, previews and image counts are loaded for selected winners rather than the whole corpus.
7 — Attach hierarchy only on demandinclude_hierarchy=false avoids hierarchy loading. When true, ancestors and all-level descendants are navigation metadata, not evidence.
8 — Focus section evidenceThe global matched block is preferred, then search_section_evidence selects bounded additional evidence inside each winner.
9 — Pack grouped evidenceReturn documents[].sections[].blocks[] under one byte budget. Public document identity is document_id.
search(
    query,
    workspace_id,
    document_id=None,
    top_k=5,
    exclude_section_ids=None,
    include_hierarchy=False,
)
Important production change: one search call is one retrieval pass. There is no server-side rewrite loop and no suggested_files output. The agent decides whether a second search is justified.

7. Hybrid retrieval and ranking

Block evidence

75%

Hybrid RRF built from block semantic and lexical candidates. This is the dominant ranking signal.

Section title

20%

Section-title semantic/BM25 rank gives structural topic context.

Filename

5%

Internal routing signal only. Default split with semantics enabled: 3% deterministic text + 2% semantic filename rank.

Filename behavior developers must know

  • Generic terms such as report, annual or document do not narrow document scope.
  • Structured issuer patterns such as ISSUER_2025... can be recognized; a confident exact issuer match can narrow discovery to those document IDs.
  • FY/fiscal-year and 10-K/10-Q forms are normalized.
  • Optional filename semantics are bounded by SEARCH_FILENAME_SEMANTIC_MAX_FILES=100 and a 5-second stage timeout by default.
  • Filename signals are routing context, not evidence and are not returned as suggested_files.

Scores rank evidence; they are not confidence probabilities.

8. Production scalability path

The main production optimization is architectural: avoid moving corpus-scale scope state into Python.

SearchScope responsibilities

  • Build the canonical authorized document predicate once per request.
  • Detect single-document scope with at most two identity rows so diversity rules stay compatible.
  • Discover distinct FTS configurations without materializing all document metadata.
  • Keep issuer narrowing and normalized filename token overlap in SQL.
  • Expose direct workspace filtering for child tables when safe.
  • Hydrate document metadata only for bounded candidate document IDs.

Production index additions

IndexWhy it exists
idx_documents_filename_tokensGIN lookup of normalized filename tokens.
idx_documents_filename_issuerExact normalized issuer lookup.
idx_documents_workspace_filename_orderBounded workspace filename preselection.
idx_documents_workspace_ftsScoped language/config discovery.
idx_blocks_doc_page_idOrdered document/page reading.
Feature flag: SEARCH_SCALABLE_SCOPE_ENABLED=true is the production default. Setting it to false restores the legacy request-local metadata path for rollback/debugging; the extra indexes may remain installed.

9. Focused retrieval with search_in_sections

Once global search has found a large relevant section, the next question is often not “read everything”, but “find the exact prerequisite / exception / amount / clause inside this section”. That is the role of search_in_sections.

Public behavior

  • Accepts up to 10 numeric public section IDs.
  • Ranks evidence independently inside each exact section.
  • Returns exact text or image descriptions with IDs.
  • Can include one previous and one next text block around each selected hit.

Local scoring

For text blocks, the helper computes approximately:

0.7 × semantic_similarity
+ 0.3 × lexical_rank(title + content)

The discovered global hit can be flagged as preferred so it is not accidentally dropped.

Why title context matters: a block containing “120 EUR” may not repeat “cancellation penalty”. By scoring section title + block content, the local search keeps the subject context.

Neighbor logic

previous block→ ranked hit→ next block

Neighbors are there to avoid dropping adjacent exceptions or continuation sentences. They are optional evidence and are packed after ranked hits.

11. Agent-controlled follow-up search

There is no server-side iterative-search state anymore. One search call means one retrieval pass. The agent decides whether another call is necessary after inspecting evidence and omissions.

Follow-up rules

  • Inside known sections: prefer search_in_sections, read_sections or read_blocks.
  • Outside known sections: issue a new focused search, preserving workspace and known document IDs.
  • Need different sections: optionally pass prior public section IDs as exclude_section_ids=[101088,101056].
  • Exclusions are stateless: the agent must accumulate and resend them. They filter both section and block candidate channels before their limits.
  • Do not exclude when revisiting or validating evidence already found.
  • Stop when another call would not close a material evidence gap.
# initial
search(query="renewal conditions", workspace_id="legal", document_id=["doc-42"])

# follow-up only if a different area is needed
search(
  query="automatic renewal notice period",
  workspace_id="legal",
  document_id=["doc-42"],
  exclude_section_ids=[101088, 101056]
)

12. Evidence budgeting — why responses stay small

Excerpt

1,000 chars

Default maximum exact excerpt size per selected block.

Search payload

24 KB

Default serialized JSON byte budget shared by grouped search evidence.

Section hits

3

Default primary block evidence per selected section before optional neighbors. The grouped output uses document IDs rather than filenames.

How the packer works

  1. Group sections under documents and deduplicate section IDs.
  2. Build ranked evidence lists and exact serialized byte sizes.
  3. If metadata does not fit, trim optional navigation first.
  4. If necessary, omit trailing sections with an explicit sections_omitted count.
  5. Allocate ranked primary hits round-robin across sections.
  6. Allocate optional adjacent evidence only after primaries.
  7. Restore source order inside each section.
  8. Set budget_exhausted and has_more_blocks truthfully.
Design rule: response limits must reduce payload, not create fake completeness. Any optimization that removes evidence must preserve an explicit way to detect and retrieve what was omitted.

13. Data model used by navigation

Do not confuse IDs. logical_sections.id is the public numeric section ID used by navigation tools. logical_sections.section_id is the document-local parser key. Citations use block or image IDs — never section IDs.

14. Search result contract

The production MCP response deliberately exposes stable indexed IDs and exact evidence, while removing filenames from the model-facing tool payload.

{
  "documents": [
    {
      "document_id": "66f0b9...",
      "workspace_id": "ws-1",
      "sections": [
        {
          "section_id": 14390,
          "title": "Penalties",
          "rank": 1,
          "score": 0.84,
          "blocks": [
            {
              "block_id": 91231,
              "page_number": 14,
              "score": 0.84,
              "content": "If delivery is delayed ...",
              "content_truncated": false
            }
          ],
          "has_more_blocks": true,
          "ancestors": [ ... ],       // only if include_hierarchy=true
          "descendants": [ ... ]
        }
      ]
    }
  ],
  "budget_exhausted": false
}
No suggested_files contract: filename relevance is now an internal ranking signal. If the agent needs a broader or different search, it reformulates the query or narrows with known document_id values; it does not follow filename suggestions from the tool.

Fields that mean “keep investigating”

content_truncated

Selected block is only a preview. Use read_blocks when the omitted text could affect the answer.

has_more_blocks

Section contains additional block evidence beyond the returned ranked selection.

sections_omitted

Some ranked sections did not fit the shared response budget.

budget_exhausted

The packer trimmed navigation/evidence or whole sections.

not_evaluated

A bounded read batch could not process this input under its current budget/deadline.

hierarchy_issues

Context traversal found missing references or cycles; structural completeness is not guaranteed.

15. Citation lifecycle

Citation lookup is a validation phase, not a discovery phase.

Retrieve evidence→ Resolve all answer gaps→ Build citation items→ locate_answer_citations→ Final answer 
{
  "type": "text",
  "block_id": "14579",
  "evidence_text": "exact text copied from the retrieved block",
  "reference": 1
}

The locator uses logical_text_positions for page/word coordinates where available. The Mistral path has a dedicated variant because source positioning differs.

Invariant: citation lookup must be the final retrieval tool call. Do not navigate or search after citations have been finalized.

16. Security and workspace scope

Transport authentication

Authorization: Bearer <MCP_API_KEY>
Workspace-Id: finance, legal

The tool's workspace_id must be contained in the effective authenticated scope.

Document scoping

Known documents are scoped with indexed document_id values. Section/block/image tools resolve owning documents from their unique IDs; they do not accept document_id.

Security invariant: workspace/document predicates belong in the candidate SQL. Never broaden retrieval and filter authorization afterward. The scalable path exists partly to preserve this rule without materializing large authorized scopes in Python.

The MCP API key is still a trusted service credential. Repository documentation notes that deployments with user-specific ACLs must resolve permitted scopes upstream or through a server-side identity/ACL resolver; the logical_documents.user_id column is not the MCP authorization mechanism.

Embedding provider unavailable / model queue occupiedSupported search paths can continue lexical-only.Dependency failure must not masquerade as “no evidence”.

18. Debug playbook

Search returns the wrong document

  • Confirm workspace_id and optional document_id scope passed to the tool.
  • Check whether SEARCH_SCALABLE_SCOPE_ENABLED is on and inspect the SearchScope predicates.
  • Inspect filename issuer narrowing separately from content ranking.
  • Confirm the issue is not public logical_sections.id versus local parser section_id.

Good section, wrong block

  • Inspect the globally preferred block and search_section_evidence winners.
  • Compare block semantic versus lexical components.
  • Check whether the section title contributes expected lexical context.
  • Check has_more_blocks before concluding evidence is absent.

Latency spike

  • Separate scope preparation, embedding, translation, filename semantics, candidate SQL, hierarchy and evidence hydration timing.
  • Check DB/model queue wait and overload errors before increasing worker counts.
  • Verify hierarchy was not enabled unnecessarily.
  • Compare SEARCH_SCALABLE_SCOPE_ENABLED=true and false on the same corpus/query.
  • Inspect broad mixed-language BM25 queries; current production docs identify them as a remaining ceiling.

Agent repeats searches

  • There is no server loop: inspect the agent policy and actual tool trace.
  • For gaps inside known sections, use local/read tools rather than another global search.
  • For a genuinely new global area, use a reformulated query and optionally exclude_section_ids.
  • Stop when repeated calls add no new evidence.

Production commands

# unit + configured integration tests
python -m unittest discover -s tests

# verify required DB extensions / indexes without applying changes
python -m scripts.setup_database

# apply missing supported search indexes
python -m scripts.setup_database --apply

# real MCP load test (can incur model cost)
python -m scripts.load_test_search \
  --url http://localhost:8045/http/ \

21. Golden rules

1Scope before ranking.

Never retrieve broadly and filter security scope afterward.

2Search before read.

Targeted questions use one search pass first; known documents are scoped by document ID.

3Read when completeness requires it.

Top-ranked evidence is not automatically a full procedure or exhaustive list.

4IDs are contracts.

Document IDs scope documents; public section IDs navigate/exclude; block/image IDs cite.

5Budgets must be truthful.

Every omission needs an explicit signal and retrieval path; citation lookup remains terminal.

6Follow-up is agent controlled.

No hidden server loop: issue another search only for a concrete unresolved gap.
