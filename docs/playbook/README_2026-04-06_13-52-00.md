# Playbook Architecture

> **Slug:** `playbook` | **Status:** 🚧 draft | **Last Updated:** 2026-04-06 13:52:00

## Purpose
Document the playbook execution system and the integration points an AI coding agent needs to extend it safely.

## Scope
Includes frontend streaming behavior, backend workflow execution, gRPC stream consumption, cancellation handling, replay, evaluation, workflow result export, and playbook generation prompts.
Excludes unrelated modules outside the playbook domain.

## Architecture
Playbook workflow execution runs through a gRPC server-streaming call from Nest to the ADK service. The backend buffers step updates, forwards them to the frontend over SSE, and finalizes the execution when the gRPC stream terminates.

Prompt templates are now managed through the playbook prompt registry. The backend resolves the latest enabled templates, serializes them into `prompt_overrides`, and passes them through gRPC so the ADK can apply them when building task prompts, structured-output routing prompts, replay prompts, and the playbook generation preprompt.

Clarification context is also persisted in playbook execution state: `clarification_transcripts_by_task` stores the turn-by-turn HITL transcript and `task_description_overrides_by_task` stores the clarified task text. On resume, `graph_builder._get_clarification_context()` restores both values and `_store_clarification_context()` writes them back into the checkpointed state, so resumed clarification runs do not re-ask the same clarification.

The stream finalization path now distinguishes between:

- genuine premature stream termination while work is still pending
- locally cancelled streams that end without emitting a gRPC `error` event

## Requirements
- As a user, I want workflow execution to stay responsive while live progress streams.
- As a user, I want a manually stopped workflow to finish as `cancelled`, not `failed`.
- As a backend consumer, I want locally cancelled gRPC streams to finalize correctly even when the client library emits `end` instead of `error`.
- As a user, I want resumed HITL clarification runs to reuse the stored clarification transcript and task description override so the same clarification is not asked twice.
- As an admin, I want to edit playbook prompts, including the generation preprompt, so new playbook drafts can use updated instructions without redeploying.

## API / Interfaces
- `PlaybookExecutionService.consumePlaybookStream()` consumes the full-workflow gRPC stream and decides whether to complete, interrupt, cancel, or fail the execution.
- `PlaybookGrpcService.markCancelled(executionId)` marks an execution as locally cancelled before the Nest client calls `cancel()` on the active stream.
- `PlaybookGrpcService.wasCancelled(executionId)` is now consulted from both the stream `error` path and the stream `end` path.
- `markExecutionCancelled()` emits `playbook_execution_complete` with `status: cancelled` and skips still-running/pending tasks.
- `PlaybookDesignService.generatePlaybook()` and `designPlaybook()` now attach `prompt_overrides` from the prompt registry to the gRPC request.
- `ExecutionState` includes `clarification_transcripts_by_task` and `task_description_overrides_by_task` so clarification context survives LangGraph checkpoint resume.
- `graph_builder._get_clarification_context(state, task_id)` restores the persisted clarification transcript and task description override for a task.
- `graph_builder._store_clarification_context(state, task_id, transcript, task_description)` persists the clarification context back into execution state.
- `ChatbotServicer._build_generate_playbook_prompt()` now accepts registry overrides and prepends the `playbook.generate` preprompt before the DAG instructions.

## Design Decisions
| Decision | Rationale | Alternatives Considered |
|----------|-----------|------------------------|
| Check the local cancellation flag inside the stream `end` handler | Some gRPC client cancellations complete via `end` without surfacing an `error`, so the backend must not treat that path as an unexpected workflow failure | Only handling cancellation in the `error` handler |
| Keep premature-end failure logic for non-cancelled streams | Unexpected stream termination with pending/running tasks is still a real execution failure signal that the UI should surface | Treating every ended stream as cancelled or successful |
| Route playbook prompts through `prompt_overrides` | Keeps prompt edits in the same registry and lets the ADK reuse one payload for task prompts, replay prompts, routing prompts, and generation preprompts | Separate config source for generation prompts |
| Persist clarification transcripts and task description overrides in execution state | Resumed HITL runs need the original clarification context to replay cleanly instead of asking the same question again | Rebuilding clarification context only from the in-memory interrupt payload |
