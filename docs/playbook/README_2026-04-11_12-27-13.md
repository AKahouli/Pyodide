# Playbook Architecture

> **Slug:** `playbook` | **Status:** 🚧 draft | **Last Updated:** 2026-04-22 00:00 UTC

## Purpose
Document the playbook execution system and the integration points an AI coding agent needs to extend it safely.

## Scope
Includes frontend streaming behavior, backend workflow execution, gRPC stream consumption, cancellation handling, replay, evaluation, undo/redo, HITL copilot, prompt registry behavior, copilot response input handling, backend crash diagnostics, stream error-containment behavior, ambiguous artifact routing resolution, post-execution judge/reflection flows, failure cleanup for interrupted workflows, terminal execution refresh after completion events, live step-result pane resets, optimistic panel focus when rerunning or resuming a step, stale completion poll protection, clearing stale payloads when a step re-enters `running`, visible-status handling during active reruns, advisor autopilot forwarding when rerunning a specific step for evaluation, rerun-time clearing of stale advisor state, latest-history selection for evaluation and advisor result panes, and the implemented port-unification slice for additive payload scaffolding and dual-write plumbing.

## Implementation Notes
- Playbook execution requests now accept `runNodeReflection`.
- Execution state stores reflection and judge summary metadata alongside task-level judge status, result, error, and history.
- `PlaybookJudgeEnrichmentService` schedules node reflection asynchronously after step completion, re-sweeps completed executions, enqueues pending node judges so the limiter can process them in parallel, and uses explicit per-call LiteLLM timeouts for node judge, execution summary, and rewrite requests.
- In the workflow stream path, completed steps are flushed to persistence before semantic evaluation and node reflection are scheduled, so node judge work can start immediately after each node completes.
- When a workflow fails unexpectedly, still-running task rows are terminalized to `FAILED` and the remaining pending rows are marked `SKIPPED`, so the execution cannot surface a node as both running and failed at the same time.
- The frontend now refetches the execution after the terminal completion SSE so the persisted backend task states win over any stale optimistic or missed stream state.
- When a step re-enters `running`, the optimistic task payload now clears output, artifacts, tool traces, prompt traces, semantic match, and judge data so the pane does not keep showing the previous completed result.
- The backend rerun reset now also clears the current task’s `judgeStatus`, `judgeResult`, and `judgeError`, so a rerun cannot short-circuit the next synchronous advisor pass with stale `evaluated` state from the previous attempt.
- The execution rerun path now also refreshes `reflectionEnabled` from the current request so the reused execution record stays aligned with the toolbar Advisor toggle.
- The step-result pane now resets to the live in-flight attempt when a step re-enters `running`, which prevents the previous completed attempt from lingering in the selected result view.
- Rerun and resume actions now optimistically focus the relaunched execution in the visible panel whenever the user is on that playbook page, so the panel header and step list immediately switch to `running` instead of staying on an older completed execution.
- The canvas page, execution header, and execution panel now derive a visible execution status from task results so a rerun/resume attempt presents as `running` or `interrupted` even while the persisted execution shell still says `completed`.
- The step-evaluation rerun action now forwards the advisor autopilot settings so a specific-step evaluation still triggers the advisor branch when advisor mode is enabled.
- Rerun and resume actions also clear any pending judge-refresh timer for the same execution, and the execution merge now keeps a newer optimistic `running` attempt over an older fetched `completed` snapshot.
- The frontend no longer eagerly refetches the same execution immediately after a rerun/resume API call; SSE updates and the completion-time fetch now own the authoritative transition back to terminal state.
- The frontend merge logic preserves richer cached judge state over stale fetched task rows with the same step status, so `evaluating` and `evaluated` badges are not reset back to `idle` during active runs.
- The frontend still polls completed executions briefly so judge results appear if the SSE stream closes before the reflection finishes.
- Judge prompts are registered through `PlaybookPromptService` for node reflection, execution summary, the two rewrite actions, and step-level optimization.
- The playbook controller exposes reflection actions to update the current playbook, generate a new optimized playbook, or optimize the selected step in place.
- The frontend playbook API now targets the backend rerun and resume-from-step routes exactly, matching the controller paths for execution reruns.
- Playbooks now expose a derived trigger model where `manual` is always available by default and `schedule` is the only supported automated trigger in v1.
- Backend trigger endpoints (`GET /playbooks/:id/triggers`, `PUT|DELETE /playbooks/:id/triggers/schedule`) wrap the existing embedded schedule storage so the schedule runner and persistence model remain unchanged.
- Mail trigger availability is now derived from the owner's existing Microsoft 365 mailbox readiness instead of being hardcoded unavailable, while inbound mail execution remains deferred.
- Playbooks now persist a real mail-trigger configuration through `PUT|DELETE /playbooks/:id/triggers/mail`, including basic mailbox filters (`from`, `subjectContains`, `bodyContains`, `hasAttachments`), while explicitly keeping `runtimeEnabled: false` until inbound execution is implemented.
- The backend now defines a normalized inbound mail event shape and an embedded mail-event ledger model with stable dedupe keys (`provider:mailboxAppKey:providerMessageId`) so future webhook/subscription work can record and deduplicate inbound events before execution is enabled.
- The mail event ledger is now stored in a dedicated `playbook_mail_event_ledger` collection with a unique `(playbookId, dedupeKey)` index, which avoids unbounded playbook document growth and improves dedupe safety under concurrent inbound mail bursts.
- Matched mail-trigger ledger rows can now be handed off idempotently into standard playbook execution creation using the existing execution pipeline with a new `executionTrigger: 'mail'` mode and a post-create ledger transition to `handed_off`.
- Playbook executions now persist an optional `triggerContext`, and full-workflow gRPC requests forward that payload as `trigger_context`, so future trigger-node runtime work can consume structured mail-trigger data without inventing a second execution channel.
- Owners can now test the complete backend mail-trigger pipeline without waiting for Microsoft Graph delivery by calling `POST /playbooks/:id/triggers/mail/test-event` with a synthetic simple mail payload; the backend normalizes the event, runs dedupe and filter matching, and hands matched events off into execution creation.
- A real Microsoft Graph webhook ingress path now exists for simple mailbox messages: owners can create a subscription through `POST /playbooks/:id/triggers/mail/sync-subscription`, Graph webhook validation hits `GET /playbooks/mail/webhook`, and notification batches hit `POST /playbooks/mail/webhook`, where `clientState` is checked before fetching the actual message and reusing the existing orchestration pipeline.

## UI Notes
- Canvas nodes show judge state and score badges.
- The toolbar exposes a reflection toggle for execution runs.
- The design toolbar and card shortcut now open a `Triggers` panel instead of a schedule-only panel; in v1 the automated trigger selector remains effectively `None | Schedule` by reusing the existing schedule editor.
- The trigger contract now includes a `mail` placeholder whose `available` flag reflects whether the playbook owner's Microsoft 365 connection includes the required mailbox scope foundation for future mail triggers.
- The Triggers panel now lets owners select `Mail` as the future automated trigger, save mailbox filter criteria, and see mailbox readiness messaging, but the UI still communicates that inbound mail execution is not active yet.
- The shared trigger contract now also reserves runtime-facing mail payload and workspace attachment-import metadata models, but these remain informational until the event pipeline and trigger-node execution are implemented.
- Mail-trigger ingestion now uses the dedicated ledger collection plus a lightweight orchestration service that classifies newly ingested events as `matched` or `ignored` after filter evaluation, while duplicate events are short-circuited without re-matching.
- Mail-trigger handoff currently seeds the playbook execution through the normal execution service and marks the ledger row with the resulting `executionId`, but trigger-node payload injection and attachment workspace staging are still pending runtime work.
- Mail-trigger handoff now also builds a normalized trigger payload from the ledger row and stores it on the execution as `triggerContext`; attachment download/import and explicit node-level consumption are the remaining runtime gaps.
- The new synthetic test-event route is intended for end-to-end validation with simple emails without attachments. Real Microsoft Graph webhook/subscription ingress is still pending, but it will target the same normalized orchestration path.
- The Graph path still lacks attachment download/import and stronger production hardening around callback hosting, but the simple no-attachment delivery path is now wired to the same normalize -> ingest -> match -> handoff flow used by synthetic tests.
- Auto-renewal of Microsoft Graph mailbox subscriptions is now conditioned by a user-selected `autoRenewUntil` date. The backend clamps the Graph subscription `expirationDateTime` to the earlier of the 45-minute Graph window and the user cutoff, and the renewal cron skips playbooks whose cutoff has passed. The sync-subscription endpoint rejects cutoffs that are already in the past with a clear 400 error.
- The mail-trigger execution handoff now forwards `triggerContext` end-to-end into ADK single-step and full-workflow port resolution, so mail-linked input ports can resolve against the trigger payload instead of seeing an empty context.
- When mail attachments are imported successfully, the backend now includes richer `mail_attachments` trigger-port metadata in the handoff: both `documentIds` and explicit `documents` metadata are forwarded so downstream nodes can consume the staged artifacts directly.
- The frontend mail-trigger filter editor now treats an unchecked "Only match emails with attachments" option as no filter constraint (`hasAttachments = null`) instead of forcing a false predicate.
- ADK action indexing now uses the ADK auth `/token` endpoint for access tokens instead of self-signing, and action indexing requests now include a backend-shaped `webhook_url`.
- Action nodes now emit downstream document artifacts on their declared output port for `index` actions, preserving the input document metadata and attaching indexing status metadata so downstream nodes can use the produced artifact.
- The execution detail view exposes a Judge LLM tab that shows node-level judge output, node-level judge failures, and a single recommendation pane with remediation suggestions and action buttons.
- The recommendation pane includes the `Generate new optimized playbook` action, which opens the newly generated playbook directly.
- The recommendation pane includes the `Optimize this step` action for step-scoped rewrites.
- The execution UI now scopes live execution rendering and history selection to the active playbook route, while still preserving the global execution cache for cross-route access.
- The execution store now keeps per-playbook history alongside the global history so the active panel can render only the current playbook's executions without dropping cached data for other playbooks.
- The execution detail and interrupt views now guard `currentExecution` by matching playbook id as well as execution id, preventing a foreign execution from rendering in the wrong route.
- The evaluation and advisor history selectors now default to the newest persisted entry so fresh evaluation results are visible immediately after completion.
- The gRPC playbook task contract now includes additive `PortPayload` and `ArtifactRef` messages plus `RunStepRequest.node_inputs`, `RunStepRequest.declared_output_ports`, and `PlaybookTaskResult.emitted_payloads` for the implemented port-unification slice.
- Backend request construction now populates `node_inputs` and `declared_output_ports` from `resolveNodeInputs`, while preserving the legacy request fields during the transition.
- Backend result ingestion now consumes `emitted_payloads` when present and falls back to legacy `artifacts` / `components` mapping for older responses and historical executions.
- The ADK payload serializer/deserializer now supports the unified payload envelope while remaining legacy-read compatible, so old stored data can still be projected into the new view.
