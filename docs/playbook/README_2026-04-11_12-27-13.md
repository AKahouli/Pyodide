# Playbook Architecture

> **Slug:** `playbook` | **Status:** 🚧 draft | **Last Updated:** 2026-04-11 12:27:13 UTC

## Purpose
Document the playbook execution system and the integration points an AI coding agent needs to extend it safely.

## Scope
Includes frontend streaming behavior, backend workflow execution, gRPC stream consumption, cancellation handling, replay, evaluation, undo/redo, HITL copilot, prompt registry behavior, copilot response input handling, backend crash diagnostics, stream error-containment behavior, ambiguous artifact routing resolution, post-execution judge/reflection flows, failure cleanup for interrupted workflows, terminal execution refresh after completion events, live step-result pane resets, optimistic panel focus when rerunning or resuming a step, stale completion poll protection, clearing stale payloads when a step re-enters `running`, visible-status handling during active reruns, advisor autopilot forwarding when rerunning a specific step for evaluation, rerun-time clearing of stale advisor state, and latest-history selection for evaluation and advisor result panes.

## Implementation Notes
- Playbook execution requests now accept `runNodeReflection`.
- Execution state stores reflection and judge summary metadata alongside task-level judge status, result, error, and history.
- `PlaybookJudgeEnrichmentService` schedules node reflection asynchronously after step completion, re-sweeps completed executions, enqueues pending node judges so the limiter can process them in parallel, and uses explicit per-call LiteLLM timeouts for node judge, execution summary, and rewrite requests.
- In the workflow stream path, completed steps are flushed to persistence before semantic evaluation and node reflection are scheduled, so node judge work can start immediately after each node completes.
- When a workflow fails unexpectedly, still-running task rows are terminalized to `FAILED` and the remaining pending rows are marked `SKIPPED`, so the execution cannot surface a node as both running and failed at the same time.
- The frontend now refetches the execution after the terminal completion SSE so the persisted backend task states win over any stale optimistic or missed stream state.
- When a step re-enters `running`, the optimistic task payload now clears output, artifacts, tool traces, prompt traces, semantic match, and judge data so the pane does not keep showing the previous completed result.
- The backend rerun reset now also clears the current task’s `judgeStatus`, `judgeResult`, and `judgeError`, so a rerun cannot short-circuit the next synchronous advisor pass with stale `evaluated` state from the previous attempt.
- The execution rerun path now also refreshes `reflectionEnabled` from the current request so the reused execution record stays aligned with the toolbar Advisor toggle.
- The step-result pane now resets to the live in-flight attempt when a step re-enters `running`, which prevents the previous completed attempt from lingering in the selected result view.
- Rerun and resume actions now optimistically focus the relaunched execution in the visible panel whenever the user is on that playbook page, so the panel header and step list immediately switch to `running` instead of staying on an older completed execution.
- The canvas page, execution header, and execution panel now derive a visible execution status from task results so a rerun/resume attempt presents as `running` or `interrupted` even while the persisted execution shell still says `completed`.
- The step-evaluation rerun action now forwards the advisor autopilot settings so a specific-step evaluation still triggers the advisor branch when advisor mode is enabled.
- Rerun and resume actions also clear any pending judge-refresh timer for the same execution, and the execution merge now keeps a newer optimistic `running` attempt over an older fetched `completed` snapshot.
- The frontend no longer eagerly refetches the same execution immediately after a rerun/resume API call; SSE updates and the completion-time fetch now own the authoritative transition back to terminal state.
- The frontend merge logic preserves richer cached judge state over stale fetched task rows with the same step status, so `evaluating` and `evaluated` badges are not reset back to `idle` during active runs.
- The frontend still polls completed executions briefly so judge results appear if the SSE stream closes before the reflection finishes.
- Judge prompts are registered through `PlaybookPromptService` for node reflection, execution summary, the two rewrite actions, and step-level optimization.
- The playbook controller exposes reflection actions to update the current playbook, generate a new optimized playbook, or optimize the selected step in place.
- The frontend playbook API now targets the backend rerun and resume-from-step routes exactly, matching the controller paths for execution reruns.

## UI Notes
- Canvas nodes show judge state and score badges.
- The toolbar exposes a reflection toggle for execution runs.
- The execution detail view exposes a Judge LLM tab that shows node-level judge output, node-level judge failures, and a single recommendation pane with remediation suggestions and action buttons.
- The recommendation pane includes the `Generate new optimized playbook` action, which opens the newly generated playbook directly.
- The recommendation pane includes the `Optimize this step` action for step-scoped rewrites.
- The evaluation and advisor history selectors now default to the newest persisted entry so fresh evaluation results are visible immediately after completion.
