# Smart Agent natural orchestration acceptance suite

## Purpose and method

The assessment outcomes below preserve the original baseline and repair history. Subsequent runtime fixes and current qualification are recorded in [execution repair](smart-agent-execution-repair.md) and its [browser evidence](smart-agent-execution-repair-browser-results.md); use those reports for the latest observed status.

Evaluate the existing signed-in Smart Agent in normal Conversation at http://localhost:5174. The tester is a temporary GPT-6 Sol agent; do not change Smart Agent's model or configuration for baseline testing. Smart Agent has web search, code interpreter and mono-agent-work-orchestration available. All prompts below deliberately avoid implementation terms. Do not coach the agent into using a named tool or skill after an unsuccessful attempt.

Record the actual model/configuration shown, conversation IDs, submitted prompts, wall-clock submit/acknowledgement/completion times, visible tool/activity names, Tasks state, result attribution, unexpected errors and screenshots. Use browser UI for all user interactions. Primary may corroborate execution type and status through read-only repository/database evidence; a prose promise alone is not proof of execution. Never infer parallelism from a fast answer.

Use fresh, clearly titled QA conversations with Smart Agent for independent cases; preserve existing user conversations and drafts. Reuse the same conversation where specified. One browser owner at a time. Do not send email, publish, purchase, change permissions or delete user data. All work is public research or synthetic data. Finish or cancel test work, and reset viewport overrides before handoff.

## Scoring and gates

Score each applicable dimension 0 (failed), 1 (partial) or 2 (passed): correct execution choice; automatic capability discovery; truthful status/results; answer correctness/evidence; conversation responsiveness; continuity/attribution; cancellation/recovery. Record latency values rather than claiming a universal performance SLA. Flag visible acknowledgement over 10 seconds and simple interleaved answer over 15 seconds for investigation, accounting separately for provider delay and application blocking.

Critical failures: cross-conversation data or answer mixing, unintended external action, loss of draft/message, incorrect cancellation of unrelated work, false claim of a completed artifact/job, silent dropped submission. Major failures: avoidable foreground blocking, repeated duplicate jobs/results, no autonomous use of available orchestration for substantial independent work across the suite, broken clarification, inaccessible results, or factually incorrect calculation.

Gates are PASS, FAIL (verified product/behavior defect), BLOCKED (environment/capability unavailable), SKIPPED (not applicable with reason). Distinguish model choice from runtime availability and UI defects. Full potential means appropriate capability selection, not forcing every request through every tool.

Run baseline before tuning. Primary diagnoses failures against source and execution evidence, makes the smallest skill/code change, and reruns failed cases plus one adjacent regression using fresh wording. After two unsuccessful repair cycles on the same gate, stop that gate and report evidence. Final report must separate observed passes, blocked capabilities, remaining defects and untested behavior; a finite test suite cannot establish universal agent reliability.

Direct answers, arithmetic, clarification and overlapping replies passed. Substantial research and the four-item batch stayed in the foreground despite enabled capabilities. Follow-up turns lacked the completed answer's citation mapping.

### Final assessment outcome

**Useful autonomous research completion: FAIL.** The fresh single-assignment test automatically submitted a temporary background worker, answered concurrent arithmetic correctly, and preserved a draft through final publication. However, the worker performed no retrieval and returned no text, evidence or artifacts; the final chat candidly reported this. A strict finite-item prompt automatically submitted a background fan-out with four stable items and two temporary workers, but sampled events showed repeated choice-tool calls and zero research. After the tester stopped the batch specifically, final UI accounting was two completed items with empty results and two stopped items; all QA work became terminal. The final prose reported three cancelled tasks, creating an unresolved difference from the two stopped child items (possibly including the coordinator).

**Conversation continuity/navigation, natural ordinary-reply cancellation, autonomous dispatch and bounded worker admission: PASS in observed cases.** Source/build/unit/review/maintainer gates pass. These do not certify the agent's full research capabilities. Final completion repairs stop under AGENTS.md's two-unsuccessful-cycle rule. Remaining diagnosis is tool selection/execution in the configured live worker; native history is retained and both standalone and fan-out workers reach the shared compiler guard. Natural cancellation of the earlier stuck batch and the minor baseline UX issues remain unqualified/unfixed as documented. No universal reliability claim is warranted.

Minor baseline UX observations retained for assessment: live tool response unavailable until completion, stale destination choice after a prose answer, blank clarification reply pointing to Tasks, and missing model label on one resumed result. These are not counted as fixed by the changes above.
