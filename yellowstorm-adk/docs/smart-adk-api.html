1. Aperçu général

Version: V1

BasePath par défaut: http://localhost:8001

L’API FastAPI Smart ADK API expose deux routes regroupées sous les préfixes /chatbots et /agentic. Chaque route retourne une réponse diffusée par flux SSE, permettant d’afficher en temps réel la production des agents cognitifs.[1]

2. Authentification & sécurité

Toutes les routes exigent un jeton Bearer valide. Le service d’authentification repose sur le flux OAuth2 Password : FastAPI fournit un schéma OAuth2PasswordBearer dont l’URL du jeton est {API_URL}token. Le jeton JWT doit être présenté dans l’en-tête Authorization: Bearer <token>.[2]

Lorsqu’une requête arrive :

  • le jeton est validé et décodé pour récupérer l’identifiant utilisateur,
  • les informations du compte sont chargées depuis Redis,
  • si l’utilisateur est inactif ou inconnu, une erreur 401 ou 400 est levée.

3. Format de réponse Server-Sent Events

Les deux endpoints retournent une réponse de type text/event-stream. Chaque événement SSE encapsule un objet JSON sérialisé via la clé data:.[1]

Structure générale d’un événement

Champ Type Description
agent_id string Identifiant interne de l’agent émetteur (si disponible, sinon "no_id").
agent_name string Nom de l’agent (« manager », « system », etc.).
agent_type string Type fonctionnel (manager, agent, html, suggestions, ...).
chunk string Contenu diffusé (texte, JSON ou indicateur end_of_message).
message_id string Identifiant du message courant dans la conversation.
message_type string streaming pour les flux en continu, no-streaming pour les messages système, ou error en cas d’incident.[3]
content_type string Nature du contenu : chunk, description, function_call, source, File, error, final_response, suggestions, etc.[3], [4]

Exemple de trame SSE reçue par le client : 

data: {"agent_name": "manager", "agent_type": "manager", "chunk": "Bonjour, que puis-je faire pour vous ?", "message_id": "...", "message_type": "streaming", "content_type": "chunk"}

4. Gestion des erreurs

  • 401 Unauthorized – jeton invalide ou utilisateur inexistant.[2]
  • 400 Bad Request – utilisateur authentifié mais inactif.[2]
  • 422 Unprocessable Entity – erreur de validation Pydantic (schéma JSON incorrect).
  • 500 Internal Server Error – exception inattendue durant le traitement asynchrone.[1]

Pipeline RAG

5. Pipeline RAG – Indexation & Recherche

Vue d'ensemble

Le système RAG (Retrieval Augmented Generation) expose une API REST complète pour l'indexation et la recherche de documents. Il est organisé autour de deux phases principales : l'indexation (ingestion, traitement et stockage vectoriel) et la recherche (récupération intelligente via différentes stratégies). L'orchestration asynchrone repose sur Celery et le backend de stockage sur Azure AI Search. 

flowchart LR
    A[Fichier source] --> B[Chargement]
    B --> C[Découpage]
    C --> D[Vectorisation & Stockage]
    E[Requête utilisateur] --> F[Recherche vectorielle]
    E --> G[Recherche full-text]
    F --> H[Fusion RRF]
    G --> H
    H --> I[Résultats pertinents]

5.1 Indexation

Architecture de l'indexation

L'indexation suit un pipeline asynchrone orchestré par Celery. Chaque étape est une tâche indépendante chaînée via celery.chain. 

flowchart TD
    A[Fichier source] --> B[Chargement]
    B -- OCR optionnel --> C[Découpage / Chunking]
    C -- Style-aware configurable --> D[Vectorisation & Stockage]
    D --> E[Azure AI Search]
    B -- Extraction d'images --> F[Pipeline images]
    F -- YOLO / docseg --> G[Description LLM]
    G --> D

Pour l'indexation standard, trois options sont disponibles :

  • Option 1 – Style-aware chunking (PDF) : découpage intelligent basé sur la structure visuelle du PDF
  • Option 2 – Chunking standard : téléchargement → chargement → découpage → stockage
  • Option 3 – Avec description d'images : chaîne principale + chaîne images parallèle (YOLO → extraction → description LLM)

Étapes du pipeline d'indexation

Étape 1 : Chargement – Support multi-formats avec détection automatique :

FormatExtensionTraitement
PDF.pdfPyPDF / OCR optionnel, extraction d'images
Excel.xls, .xlsxChargement cellule par cellule
PowerPoint.ppt, .pptxExtraction texte par slide
Word.doc, .docxExtraction texte structuré
TexteautresChargement texte brut

Étape 2 : Découpage – Deux stratégies disponibles :

  • Chunking standard : RecursiveCharacterTextSplitter avec taille, chevauchement et séparateurs paramétrables
  • Chunking avec préservation de l'ordre : ajoute metadata.order et metadata.start_index pour la reconstruction post-recherche
  • Style-aware chunking (PDF Azure Data Lake) : découpage basé sur la structure visuelle (titres, sections, tableaux)

Étape 3 : Stockage – Indexation unitaire ou par batch dans Azure AI Search avec support des champs vectoriels et textuels.

Traitement avancé des images

Pour les PDF avec image_description=true, une chaîne Celery parallèle traite les images :

flowchart TD

    B --> C[Détection d'objets YOLO/docseg]
    C --> D[Post-traitement & fusion des boîtes]
    D --> E[Extraction des sous-images]
    E --> F[Upload vers Azure Data Lake]
    F --> G[Description LLM des images]
    G --> H[Création documents avec métadonnées]
    H --> I[Indexation dans la même collection]

Métadonnées d'image stockées : type, page, image_path, aspect_ratio, plus les métadonnées source du document parent.

5.2 Recherche (Retrieval)

Stratégies de recherche disponibles

Recherche vectorielle – Recherche sémantique par similarité vectorielle. Retourne les documents accompagnés de leur score de distance.

Recherche full-text – Recherche lexicale par mots-clés (BM25 sous Azure AI Search). Disponible uniquement avec le backend Azure AI Search.

Recherche hybride – Combine recherche vectorielle et full-text via Reciprocal Rank Fusion (RRF) avec exécution parallèle des deux recherches.

flowchart TD
    A[Requête utilisateur] --> B[Recherche vectorielle]
    A --> C[Recherche full-text]
    B --> D[Fusion RRF]
    C --> D
    D --> E[Résultats rerank&e9;s]

Paramètres spécifiques de la recherche hybride :

ParamètreDescriptionDéfaut
rrf_kConstante de fusion RRF60
vector_search_top_kNombre de résultats vectoriels—
full_text_search_top_kNombre de résultats full-text—
vector_search_weightPoids recherche vectorielle1
full_text_search_weightPoids recherche full-text1

Recherche multilingue – Accepte un dictionnaire de requêtes par langue, exécute la recherche pour chaque langue et fusionne les résultats selon la strat&e9;gie configur&e9;e.

Recherche multi-query

Toutes les stratégies supportent des variantes « multi » qui acceptent plusieurs requêtes simultanées. Chaque requête est exécut&e9;e en parallèle via des tâches Celery distinctes, puis les résultats sont fusionnés via RRF avec poids égaux pour retourner le top-k global.

flowchart LR
    A[Requête 1] --> B[Tâche Celery 1]
    C[Requête 2] --> D[Tâche Celery 2]
    E[Requête N] --> F[Tâche Celery N]
    B --> G[Fusion RRF]
    D --> G
    F --> G
    G --> H[Top-k global]

Filtres et métadonnées

Les filtres sont des dictionnaires traduits selon le backend :

  • Azure AI Search : syntaxe OData / filter Azure

Exemples de filtres courants : external_id, source, type (text/image).

5.3 Post-traitement

Réordonnancement contextuel long – Réordonne les documents pour optimiser la pertinence dans un contexte LLM long. La strat&e9;gie place les documents les plus pertinents au début et à la fin du contexte.

Reconstruction de documents – Pour chaque document retourné, le système recherche tous les chunks du même titre et external_id, les trie par metadata.order et les concatène dans l'ordre pour reconstruire le document complet. Une variante multilingue existe avec support de collection spécifique par langue.

5.4 Gestion des collections

Requêtage par filtres – Recherche de documents par filtres sans requête textuelle, avec projection de champs (include / exclude).

Suppression – Trois endpoints sont disponibles :

  • DELETE /delete-by-filter : suppression par filtre
  • DELETE /delete-by-ids : suppression par IDs
  • DELETE /delete-collection : suppression d'une collection entière

5.5 Prétraitement utilitaire

POST /split-documents – Endpoint synchrone pour découper des documents sans les indexer. Utile pour prévisualiser le chunking avant indexation.

5.9 Points d'attention et bonnes pratiques

Chunking

  • Taille des chunks : 1200 tokens est la valeur par défaut, à ajuster selon le modèle LLM cible
  • Chevauchement : 0 par défaut, peut être augment&e9; pour préserver le contexte entre chunks
  • Séparateurs : ordre d&e9;croissant de priorit&e9; pour pr&e9;server la structure du document

Performance

  • Les tâches d'indexation sont asynchrones : utiliser /task/{id} pour le suivi
  • La recherche hybride exécute vector + full-text en parallèle
  • Le traitement d'images utilise un ThreadPoolExecutor configurable

Limitations connues

  • Suppression de collection non impl&e9;ment&e9;e pour Azure AI Search
  • La gén&e9;ration de graphes (brain_type="graph") nécessite des paramètres chunk_styles

Sécurit&e9;

  • Les fichiers upload&e9;s sont stock&e9;s temporairement dans ./tmp/{uuid}/
  • Nettoyage automatique via tâche périodique Celery
  • Pas de validation de type MIME, seule l'extension est v&e9;rifi&e9;e
