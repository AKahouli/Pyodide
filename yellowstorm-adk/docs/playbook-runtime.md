# Playbook ADK Runtime

## Scope

This document covers the Playbook execution runtime inside `Yellowstorm-adk`.

Main implementation areas:

- `src/grpc_server/chatbot_servicer.py`
- `src/langgraph_engine/workflow_service.py`
- `src/langgraph_engine/graph_builder.py`
- `src/langgraph_engine/step_executor.py`
- `src/langgraph_engine/state.py`
- `src/langgraph_engine/playbook_queue.py`
- `src/langgraph_engine/graph_cache.py`
- `src/langgraph_engine/checkpointer.py`

## Runtime Responsibilities

The ADK is responsible for:

- receiving gRPC execution requests
- building or reusing a dynamic LangGraph
- executing tasks with tools or direct LLM calls
- handling replay-aware execution modes
- suspending for human input when required
- resuming interrupted workflows
- streaming step updates back to the backend

## Workflow Entry Points

The primary workflow path is:

- `ChatbotServicer.RunPlaybookWorkflow`

Related paths:

- `ResumePlaybookWorkflow`
- `RunStep`
- `ResumeStep`
- `StopPlaybookWorkflow`
- `EvaluateSemanticMatch`

## Dynamic Graph Construction

`graph_builder.py` builds a graph from the playbook DAG.

Behavior:

- one graph node per task
- edges derived from the playbook edges
- multiple entry tasks are handled through a synthetic parallel start node
- completion is coordinated through a final node

## Task Node Lifecycle

Each task node broadly does the following:

1. emit `in_progress`
2. run clarification gate if enabled
3. interrupt before execution if approval is required
4. gather dependency context
5. build prompts from task, agent, query, and workspace context
6. choose live or replay execution mode
7. execute
8. interrupt after execution if review is required
9. emit final result or suspension

## Replay Modes

Current execution modes include:

- `live`
- `replay_strict`
- `replay_flex`
- `replay_adaptive`

These are implemented in the runtime so the backend can keep one consistent orchestration model while switching task behavior.

## HITL Semantics

The runtime uses LangGraph `interrupt(...)` for:

- clarification
- approval before execution
- review after execution

Special case:

- `approved = false` plus reason `__SKIP_STEP__` is treated as a skipped task instead of a failure

## Queue and Cancellation

`playbook_queue.py` stores:

- `thread_id -> queue`
- `thread_id -> task`

This supports:

- live step-update streaming
- workflow cancellation by thread id
- clean stream shutdown on stop

## Checkpointing and Resume

Resume behavior depends on:

- PostgreSQL checkpoint persistence
- thread graph retention

Without those two pieces, a suspended workflow cannot be resumed with full LangGraph continuity.

## Flow Engine Runtime

The current Playbook Flow gRPC runtime is implemented under `src/flow_engine/`:

- `builder/` composes sequential, parallel, conditional, iterator, and human-approval topology with low-level `StateGraph` APIs.
- `runtime/invoker.py` preserves the `updates` and `custom` stream modes and normalizes each part to the existing `_mode` / `_data` envelope.
- `runtime/checkpointer.py` uses `AsyncPostgresSaver` with a bounded Psycopg pool. Tables are isolated in the validated `LANGGRAPH_CHECKPOINT_SCHEMA` schema.
- `runtime/checkpoint_fork.py` selects and forks exact historical checkpoints for `RunFromCheckpoint`.
- `grpc_service.py` implements Run, Cancel, ResumeApproval, ResumeFromStep, and RunFromCheckpoint behavior.

The legacy runtime under `src/flow_engine/legacy/` remains available and was not redesigned by the dependency migration.

Validated dependency family:

```text

langgraph-checkpoint-postgres==3.1.2

langchain>=1.3,<2

langchain-qdrant==1.1.0

```

The service logs the resolved AI runtime versions once at startup. Stream v2, state/reducer changes, and other new LangGraph runtime features remain out of scope.

Checkpoint compatibility is covered by `src/flow_engine/tests/test_langgraph_1x_compatibility.py`. The checked-in SQLite fixture is generated by LangGraph `1.0.1`, checkpoint `3.0.1`, and checkpoint-sqlite `3.0.3`; the upgraded runtime can inspect its ancestry and pending writes and resume its interrupt. A checkpoint generated by `1.2.9` was also resumed successfully with the old stack, establishing bidirectional compatibility for this fixture shape. The fixture generator is `src/flow_engine/tests/fixtures/generate_langgraph_1_0_1_checkpoint.py`.

## PostgreSQL Checkpoint Storage

The Flow Engine reuses `DATABASE_URL` credentials and creates its own schema. Defaults:

```text
LANGGRAPH_CHECKPOINT_SCHEMA=langgraph_checkpoints
LANGGRAPH_CHECKPOINT_POOL_MIN_SIZE=1
LANGGRAPH_CHECKPOINT_POOL_MAX_SIZE=5
LANGGRAPH_CHECKPOINT_POOL_TIMEOUT_SECONDS=30
```

The database role must have `CREATE` on the configured database and usage/create privileges on the dedicated schema. Startup creates the schema with a quoted identifier, takes a schema-specific PostgreSQL advisory lock, runs `AsyncPostgresSaver.setup()` idempotently, and then opens the pool. Connection URLs and credentials are never logged.

PostgreSQL makes checkpoint state durable and shared, while the live `_active_executions` control map remains process-local. `ResumeApproval` first uses that map as a fast path. If no live stream exists, the backend queues the same execution and opens a new `Run` stream with the immutable snapshot, original thread ID, and `input_context.__playbook_resume`. `Cancel` remains limited to a stream owned by the current ADK process.

Human-approval nodes use dynamic `interrupt()` as their sole product suspension. They are not included in static `interrupt_after` compilation. Approval resumes use the canonical shape `{"decision": "approved|rejected", "payload": {...}}`; one resume completes the approval node and continues downstream without a second invocation. Replayed lifecycle events are deduplicated so restart-resume does not emit another approval request.

`RunFromCheckpoint` is an exact fork, not a normal resume. It scans source ancestry for a checkpoint where the target node is in `state.next` and its iteration counter equals the requested iteration, then copies that checkpoint into the new execution thread. Channel blobs, pending writes, and replay lineage are persisted through saver APIs. A PostgreSQL advisory lock covers fork preparation and target-state normalization across processes. A matching untouched prepared fork can be retried; an advanced or conflicting target fails explicitly. Missing exact history does not fall back to synthetic reconstruction.

For a first cutover from the previous local SQLite store, stop the ADK and preserve the SQLite file before running:

```bash
python -m scripts.migrate_sqlite_checkpoints_to_postgres /path/to/checkpoints.db
```

The migration is idempotent for checkpoint and pending-write primary keys. Verify migrated counts before restarting. Rollback requires the previous image and preserved SQLite file; checkpoints created in PostgreSQL after cutover are not visible to the old SQLite runtime.

SQLite remains installed only for fixture compatibility and one-time migration support. Compatibility tests must be rerun whenever any LangGraph checkpoint package changes.
