◆ YellowStorm · companion_ai / orchestrator architecture

One message in, a graph of agents out.

Companion AI is a CQRS turn orchestrator. A gRPC call delivers a write command and gets an ack — nothing more. Behind it, a planner LLM turns the user's message into a dependency graph of steps, Google ADK's workflow engine executes that graph with independent steps running concurrently, and every state change is projected into Postgres tables the client reads live over ElectricSQL. Results never travel back through the RPC.

Overview

The shape of it

Three ideas carry the whole design. First, the write path and the read path are separate: RunTask accepts a command and returns immediately, while the client watches progress arrive in Postgres rows. Second, the LLM decides what, deterministic code decides when — the planner emits tasks and dependencies, and a plain topological scheduler works out what may run together. Third, a step's status is a row, so five parallel steps are five independent live-updating rows rather than one blob the client has to diff.

Every step moves through the same small state machine, and those five values are the vocabulary shared by the domain model, the database, and the UI:

pending running blocked completed failed

blocked is the load-bearing one. A blocked step is not terminal, so its dependents simply never become ready — which is exactly what lets one branch pause to ask the user a question while unrelated branches keep running.

service.py · plan_turn

Lifecycle of a turn

This is a genuine sequence, so it's worth numbering. These ten steps are marked in the source as STEP N comments and echoed by the [worky] N. log lines, so a log tail and the code read in the same order. Steps 1–4 are in the servicer; 5–10 in service.py.

  1. RunTask receives the user's message
    The entry point for every turn. This RPC only ever returns an ack — no result travels back through it.
  2. claim_run(idempotency_key)
    Claimed in Postgres, not memory, so a retried command runs at most once per session even across restarts and replicas. A duplicate returns accepted=false and stops here.
  3. ack now, run the turn in the background
    The caller is told accepted=true and everything below runs on a background asyncio task. Progress reaches the client through the read model instead.
  4. new turn, or the answer to a pending question?
    If the session is waiting with an interrupt_id, this message is the user's answer → resume_turn, which skips planning and rejoins at step 8. Otherwise → plan_turn.
  5. planner LLM → Plan{ steps, depends_on }
    A tool-less LlmAgent prompted for strict JSON. It makes one binary call: chit-chat returns a direct answer with zero steps and the turn ends right here; anything needing live data, a tool, or a real deliverable becomes a plan.
  6. validate(plan) → assign_waves(plan)
    Cycles, self-dependencies, unknown ids and duplicates are rejected before any graph is built — a cyclic plan can never complete. Waves are then assigned for display grouping.
  7. project plan + steps as pending
    The client can render the full plan card before a single step has run.
  8. connectors → tools, to_workflow(plan) → ADK Workflow
    Each step becomes an LlmAgent node; depends_on becomes edges. This is the only place ADK types are constructed from domain types — and the step a resume rejoins at.
  9. Runner.run_async(...) → map events → live status
    ADK's graph engine runs independent nodes concurrently up to max_concurrency, sequences dependent ones, and joins fan-in. Each event becomes a step status row update; every ask-the-user interrupt this run raises is captured here.
  10. finalize: derive status, post the assistant reply
    Either the plan blocked (persist each parked step's interrupt id, surface its question in chat) or it finished — in which case the reply is the concatenated results of the terminal steps. It only finishes when no step is still parked, including ones parked by an earlier run.
plan.py · scheduler.py · graph.py

Three layers, one boundary

The most valuable structural decision in this module is that ADK is quarantined. Only one file imports it on the orchestration path, which is what makes the core testable without an LLM and survivable across ADK upgrades.

plan.py — the domain

Pydantic Plan and Step. No ADK, no database, no I/O. A step carries a short title for the UI card, a fuller description the executor acts on, a kind of execute or ask, and depends_on — which is the entire parallelism story.

scheduler.py — deterministic orchestration

Pure functions, no LLM and no I/O. validate runs Kahn's algorithm for cycle detection, assign_waves computes each step's longest dependency depth so steps sharing a wave are provably independent, ready_steps answers "what can run right now", and derive_status rolls step states up to a plan status.

graph.py — the ADK boundary

Translates a validated plan into a google.adk.workflow.Workflow. Everything ADK knows about this system enters here.

graph.py · to_workflow

Plan → workflow

Two rules in this translation exist because of verified ADK behaviour rather than taste, and both are easy to break by accident.

A plain node with N incoming edges fires N times. So a step with two or more dependencies is never wired directly — it's routed through a JoinNode, which fires exactly once after all its predecessors complete. ADK also requires a single terminal output, but a plan can legitimately end in several parallel leaves, so when there's more than one terminal step they're merged into a plan_done sink.

One smaller detail with teeth: ADK node names must be valid Python identifiers, but step ids are uuid hex and can start with a digit. node_name() sanitises them — and because the mapping is deterministic, rebuilding a plan from the database reconstructs an identical graph, which is precisely what makes resume work.

service.py · _apply_event

Tracking progress

ADK offers no per-node status callback, so progress is reverse-engineered from the event stream. Each event's node_info.path is parsed back to a step id, and the node's lifecycle is inferred from event shape: 

"plan_abc@1/step_a@1"  →  strip parents, strip @version  →  step_a  →  step id

first event seen for a node   →  running
ni.path in ni.output_for      →  completed, and the event text becomes the step result
Upgrade hazard

The path format and the output_for signal are observed ADK behaviour, verified against ADK 2.3.0 rather than promised by its API. If an upgrade changes either, steps go silently stuck at pending while the run itself succeeds — the failure is in the projection, not the execution, so tests that only assert on results won't catch it.

hitl.py · resume_turn

Asking the user

An ask step is deliberately not an LLM tool call. It's a FunctionNode, and the reason is subtle: a FunctionNode's interrupt id derives from its node path and is therefore stable across replays, whereas an LLM tool-call id is random on every rerun and would never match on resume.

The full cycle:

run     → node returns RequestInput(iid, question) → the run interrupts
        → step goes blocked, plan_steps.interrupt_id = iid, question posted to chat

        (the client shows the blocked step; the user replies)

resume  → next RunTask sees status=waiting → resume_turn
        → _plan_from_snapshot rebuilds the identical plan from the read model
        → run_async(new_message=Content(parts=[resume_part(iid, answer)]))
        → ADK replays completed nodes from the durable session,
          re-runs the blocked node with ctx.resume_inputs[iid] == answer

Durability is the whole point. Because ADK sessions are persisted with DatabaseSessionService rather than held in memory, a turn blocked on a question survives a disconnect, a restart, or a hand-off to a different replica — a fresh Runner can rehydrate the interrupt and carry on.

Several steps can wait at once

A wave can park more than one step, each asking its own question. Every one gets its own interrupt id — derived from the node path, so it is unique per step and stable across replays — and each is answerable on its own, from a separate run, in any order. resume_turn takes an optional interrupt_id to pick which parked step an answer belongs to; a chat reply carries no such id and answers the session's first. This is what lets a non-human answer arrive for one step while a human answers another.

One ADK behaviour makes this sharper than it looks: an interrupt is only ever emitted on the run that raises it. Resuming step A produces no event at all for still-parked step B — from that run's events alone, B is indistinguishable from a step that was never blocked. So the outstanding set cannot be derived from a run; it lives in plan_steps.interrupt_id, written when a step parks and cleared when it moves to any other status. _finalize reads it back before completing, because the completion branch marks every unfinished step completed — which would quietly finish work nobody ever answered.

sessions.interrupt_id still carries the first parked id for the chat surface, but the per-step ids are the routing truth: (session_id, step_id) identifies a pending question uniquely, across every session a user has open. Covered by tests/orchestrator/test_multi_interrupt.py, which pins the no-re-emit behaviour so a future ADK change that starts re-emitting is caught.

Waiting on the world: await_reply

Not every answer comes from the person in the chat. An await_reply step parks on exactly the same machinery, but only an incoming email reply resolves it — the mail webhook calls resume_turn with the reply body as the answer, and the node continues as if a human had typed it. The automatic path and the manual path are one code path, which is what makes "the reply never came, so the owner answers by hand" work for free.

The two kinds are told apart by the interrupt id prefix — ask: versus mail: — and the distinction is load-bearing, not cosmetic. A chat message is routed to sessions.interrupt_id, so if a mail wait were allowed to land there, typing in the chat would answer a step whose reply had not arrived and the plan would run on input the sender never sent. So only an ask: id is ever written to sessions.interrupt_id. A session parked solely on mail is blocked rather than waiting: it is waiting on the world, not on you — and it posts nothing to the chat, because there is no question to put there.

A session can hold both at once: one step asking the owner a question while another waits on a reply, each resumable independently and in any order. Covered by tests/orchestrator/test_await_reply.py.

Finding the step a reply belongs to

A reply has to reach the one step waiting for it, out of every step in every session every user has open. Nothing in the mail says so on its own: the connector's send_email wraps Graph POST /me/sendMail, which answers 202 Accepted with an empty body — no message id, no conversationId. There is nothing to correlate on after the fact, so the correlation is planted on the way out: a random token, minted per wait, carried in two places because either can be lost. 

subject  "Which company? [YW-xxxx]"      survives Re:/Fwd:, but the sender may rewrite it
body     <span style="display:none">      survives reply-quoting, but the sender may trim it

reply arrives → extract(subject, body) → token → DeliverMailReply(token, body)
              → claim_mail_wait → (session, step, interrupt)
              → resume_turn(interrupt_id) → the step continues

DeliverMailReply exists because the webhook holds a token and nothing else — only worky can turn one into a session, and its registry is not readable from the API. It is not a second way to continue a plan: it resolves, then hands off to the same resume_turn the RunTask path uses, so there is one continuation implementation with two entrypoints. Like RunTask it acks immediately and resumes in the background — the caller is answering Graph on a clock, and the resumed plan can run for minutes — and it takes user_id/session_id from the wait row, never from the caller. An unknown or already-claimed token is delivered=false, not an error: the webhook must ack Graph either way, since a 5xx makes Graph retry and eventually kill the subscription.

The token is opaque and random rather than a signed encoding of (session_id, step_id): a mail_waits row has to exist regardless — for expiry, de-duplication and the mailbox refcount — so the lookup happens either way, and a random token needs no secret to store or rotate. The registry is the only truth, and (session_id, step_id) is what it resolves to, unique across every open session.

The wait is written in two phases, and the ordering is what forces it. The token has to be in the mail, so it must exist before the send step runs — but the step that waits on the reply only parks after that. By the time there is an interrupt id to resume, the mail is long gone. So the row is written at plan projection with the token and no interrupt, and the interrupt is bound when the step actually blocks: 

project plan  → mint token, register wait   (interrupt_id NULL — nothing to resume yet)
send step     → stamps the token into subject + body
await step    → parks → bind_mail_wait_interrupt → now deliverable
reply         → claim → resume

The stamping is deterministic, and that is the point. The send step is an LlmAgent calling the connector's send_email like any other tool, so the obvious approach — tell it to include a marker — fails open: the one time the model omits it, the reply routes nowhere and the step waits forever. Instead the tool itself is wrapped for exactly the step whose mail is awaited, keeping the connector's name, signature and schema, so the executor sees the tool the connector published and never learns the token exists. Which step to wrap comes from the plan's own edge: an await_reply step depends_on the step that sends the mail it waits for.

A reply that beats the parking finds an unbound row and is not claimable — being claimed would mark it matched and resume nothing, losing the reply for good. Closing that window is what the catch-up query is for. A fresh plan on the session cancels the previous plan's waits: a reply to a superseded plan's mail has nowhere to go, and leaving the wait open would hold a mailbox subscription (and its renewals) for work nobody is doing.

claim_mail_wait is a single atomic UPDATE … WHERE status='waiting' RETURNING *, the same claim-once shape as run_idempotency. Graph retries any notification it thinks failed, so duplicate deliveries are routine, not an edge case — a second resume would answer an already-answered question and run the plan on the same reply twice.

readmodel.py

The read model

This is the read side of the CQRS split: the orchestrator projects a client-facing slice into Postgres as it runs, and the client subscribes to it through ElectricSQL. Four tables are published; two are deliberately not.

TablePublishedHolds
sessionsyesStatus, title, and the first interrupt_id while waiting on an answer.
plansyesOne row per session: title, goal, rolled-up status.
plan_stepsyesRow per step, so parallel work surfaces as independent live row updates. interrupt_id is set while that step waits on an answer — the durable record of every question still outstanding.
messagesyesThe conversation view — user turns and assistant replies.
run_idempotencynoDurable RunTask de-duplication. Internal.
mcp_tasksnoQueue of long-running MCP handles for the poller. Internal.
mail_waitsnoWhich step is parked on which email reply, keyed by routing token. Internal.
Design rule

Every projection goes through _project(), which catches and logs any exception rather than raising. A read-model write must never break an agent run — the worst outcome of a database hiccup is a stale card, not a lost turn.

GetSession exists alongside this for the one thing a live subscription can't do well: a one-shot snapshot for initial page load.

service.py · long_running.py · poller.py

Connectors & long tasks

Connectors arrive on the gRPC request and are materialised into executor tools per turn. Two decisions here are worth knowing before you touch them.

Not ADK's McpToolset

Tools are built with the app's existing create_connector_tools — per-action function tools that open a one-shot MCP connection. ADK's McpToolset is avoided on purpose: its session manager triggers Google-auth mTLS metadata probes that stall and fail when running off GCP.

Set-and-forget for slow actions

A reminder set for six hours must not be awaited inside a turn. Each connector therefore also gets a generated schedule_<connector>_task tool: it starts the action as an MCP task, gets a handle back immediately, records it in mcp_tasks, and the agent reports "scheduled" so the turn completes now. MCPTaskPoller later claims the row (SKIP LOCKED, so multiple workers are safe), reconnects using the server URL and auth headers captured at call time, and collects the result when it fires.

bootstrap.py · config.py

Wiring & config

OrchestratorRuntime is the single object the gRPC server starts and stops. It owns the asyncpg pool, initialises both schemas, builds the service and servicer, and starts the poller when enabled.

The schema split is not cosmetic. ADK's own session and event tables live in a separate adk schema, applied via search_path, because both ADK and the read model define a table called sessions. The read model itself lives in its own companion_ai database — derived from DATABASE_URL's host and credentials unless ORCHESTRATOR_READMODEL_DSN overrides it — and never in smartadk.

Status

Known gaps

Three things are honestly incomplete, and all three are marked in the code rather than hidden.

MCP task → workflow resume isn't wired

The poller's record mode works: it stores a fired result. But resuming a suspended workflow from a completed MCP task is still a spike. The resume callback logs a warning and returns False, which keeps the task pending and retryable instead of silently dropping it — and the whole path is gated off by MCP_TASKS_ENABLED=false.

GetSession drops step.title

The read model stores a short card title per step, but the snapshot response only copies description. Clients loading from GetSession rather than Electric get the long text where the card label belongs.

Step failure is inferred, not observed

On normal completion every non-terminal step is marked completed wholesale. The failed state exists in the model and the scheduler reasons about it, but nothing on the ADK event path currently sets it.
